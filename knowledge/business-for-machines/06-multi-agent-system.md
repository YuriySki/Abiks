# 06. Система: второй агент, контракты, оркестратор, архитектуры, интеграции

Главы 14–18. Часть V «Система».

## Глава 14. Когда нужен второй агент

Схема главы (пример разделения ролей): Исследователь → Стратег → Автор → Редактор → Проверяющий.

### R-14.1. Второй агент появляется из конфликта методов, данных или критериев, а не из моды
- **Правило.** Разделяйте роль, когда внутри неё сталкиваются разные методы, данные или критерии качества: исследователь ищет варианты, редактор сокращает, проверяющий сомневается.

### R-14.2. Разделение уменьшает контекст и делает ошибки адресными
- **Почему.** При слабом итоге видно, кто не собрал данные, кто неверно выбрал гипотезу, кто пропустил нарушение стандарта. У универсального агента вся цепочка скрыта внутри одного ответа.

### R-14.3. Каждый новый агент стоит координации
- **Правило.** Разделяйте там, где выигрыш в качестве или управляемости превышает цену: передачу контекста, хранение статусов, обработку сбоев, наблюдение.

### R-14.4. Тест необходимости отдельного агента
Кандидат обоснован, если выполняются все три условия:
1. Функцию можно описать отдельной деловой целью.
2. Она использует особые данные.
3. Её результат можно независимо проверить.

## Глава 15. Контракты между агентами

Схема главы (слои контракта): Задание → Пакет данных → Работа → Проверка → Статус.

### R-15.1. Мультиагентная система ломается на стыках — контракт делает передачу предсказуемой
- **Примеры поломок.** Один агент пишет эссе, второй ждёт таблицу; один считает задачу завершённой, второй не видит источников.

### R-15.2. Содержимое контракта
Схема данных; обязательные поля; статусы; версия источников; уверенность; ошибки; правило повторного запуска.

### R-15.3. Передаётся достаточный пакет, а не вся история диалога
- **Правило.** Следующая функция получает ровно то, что нужно для её работы (минимальный пакет T-4), а не накопленный контекст.

### R-15.4. Контракт нужен и человеку
- **Почему.** По контракту можно восстановить, какой агент создал результат, на каких данных и почему задача остановилась; цепочка генераций становится наблюдаемым бизнес-процессом.

## Глава 16. Оркестратор

Схема главы: Запрос → План → Назначение → Контроль → Сборка → Выдача.

### R-16.1. Сила оркестратора — в управлении работой, а не в знании предметных областей
- **Функции.** Получить задачу; определить маршрут; декомпозировать; выбрать исполнителя; контролировать готовность; обработать сбои; собрать результат.

### R-16.2. На раннем этапе оркестратор — обычный процесс автоматизации
- **Правило.** Языковая модель в роли оркестратора нужна только там, где маршрут зависит от смысла запроса и заранее неизвестен. Даже тогда лимиты, права и обязательные согласования остаются детерминированными.

### R-16.3. Оркестратор не скрывает происхождение результата
- **Правило.** Сохраняется след выполнения: какие агенты участвовали, какие источники использовали, что было отклонено, где вмешался человек.

### R-16.4. Зона ответственности оркестратора
Маршрут; контекст; лимиты; статусы; повторные попытки; эскалация; сборка ответа; журнал выполнения.

## Глава 17. Основные архитектуры

Схема главы: Цепочка → Параллель → Иерархия → Критик → Гибрид.

### R-17.1. Четыре базовые схемы и условия их применения
| Схема | Когда подходит |
|---|---|
| Последовательная цепочка | Каждый этап зависит от предыдущего; маршрут известен |
| Параллельная команда | Независимые исследования и варианты; нужны независимые мнения |
| Иерархия | Большие функции, где руководящий агент распределяет задачи; сложная декомпозиция |
| Исполнитель + критик | Высокие требования к качеству; результат можно проверить по правилам |

### R-17.2. Архитектуру выбирают по процессу, а не по моде
- **Правило.** Если шаги известны заранее — обычный workflow надёжнее свободной координации. Если задача исследовательская и маршрут меняется — агентный оркестратор даёт гибкость. Большинство рабочих систем гибридны.

### R-17.3. Сложность растёт после доказательства необходимости
- **Почему.** Каждая ветка добавляет новые состояния и способы отказа; простая схема с ясными контрактами часто превосходит эффектную сеть агентов.

## Глава 18. Интеграции: руки агента

Схема главы (лестница подключения): Поиск → Документы → CRM → Коммуникации → Действия → Системы.

### R-18.1. Данные дают понимание, интеграции — участие
- **Описание.** Через API и MCP агент читает документы, обновляет CRM, создаёт задачи, готовит таблицы, ищет информацию и запускает другие инструменты.

### R-18.2. Каждая интеграция расширяет поверхность риска
- **Правило.** Для каждой интеграции: отдельные учётные записи; минимальные права; лимиты; журналирование; тестовый контур. Общий администраторский доступ недопустим — его удобство слишком дорого обходится при ошибке.

### R-18.3. Интеграции подключаются по деловой необходимости
- **Правило.** Если результат всё равно проходит ручное согласование, на первом этапе достаточно черновика. Автоматическая запись появляется, когда она устраняет измеримую задержку и система умеет безопасно отменить действие.

### R-18.4. Лестница подключения
Файлы и поиск → чтение систем → создание черновиков → запись с подтверждением → ограниченные автодействия → межсистемные процессы.
